# I18N/RTL, UI system and accessibility: teammate report

Scratchpad (all scripts and outputs): `/tmp/claude-1000/-mnt-data-ecom-website/7c4de3cb-26c7-4c11-ad65-446883326dd9/scratchpad`. Nothing was written to `/mnt/data/ecom website`.

## 1. Position

- **RTL costs almost no CSS bytes.** I measured it. Write all layout with CSS logical properties (`margin-inline-start`, `inset-inline-start`, `text-align: start`) and set `<html lang="ar" dir="rtl">`. A Tailwind v4.3.4 build of a full storefront template came out as **3.9 KiB brotli, and that one file serves both directions**. Only 246 bytes (raw, before compression) were RTL-specific variants. Running rtlcss over that output changed nothing. Separate RTL stylesheets (rtlcss) gain nothing, so drop them. Inline the CSS in `<head>`.
- **The real RTL cost is fonts.** On Arabic pages, self-host one Arabic sans variable font. Pin it to `wght 400–700`, drop the extra axes, and subset it to the Arabic core plus Maghrebi letters plus ASCII digits and punctuation. That comes to **about 19–21 KiB WOFF2**. Use `font-display: optional` plus `<link rel=preload>` on `/ar/` pages only, and set an explicit unitless `line-height`. Default pick: **Noto Sans Arabic**, 21.0 KiB. It is the only sans candidate that covers the Algerian letters ڨ (U+06A8) and ڢ/ڧ. Do not use the Google Fonts CSS API for it: Google serves **162.3 KiB** for the same family's Arabic subset (measured).
- **French pages: zero web-font bytes by default.** Use the system font stack (Roboto on Android, SF Pro on iOS). If the brand needs a Latin display face, use one subset file (about 10–17 KiB), also with `optional`.
- **Ship no JavaScript for premium motion.** Use CSS cross-document View Transitions, `@starting-style`, scroll-driven animations, popover and `<dialog>`. Each is supported by **95–98% of Algerian mobile traffic** (caniuse Algeria usage data). Libraries I measured: GSAP core is 25.1 KiB br, GSAP + ScrollTrigger 40.6 KiB, `motion` 24.5 KiB, and `motion/react` adds about 43 KiB on top of React's 57.9 KiB. None of them pays for itself.
- **i18n is server-side only.**
  - URLs: `/fr/…` and `/ar/…`, with reciprocal hreflang plus `x-default`. Never auto-redirect on Accept-Language.
  - The language switch is a plain `<a>`.
  - Formatting uses `Intl` with the **`ar-DZ` / `fr-DZ`** locales at render time. That gives Western digits plus Algerian month names (جانفي, not يناير).
  - No client i18n runtime. i18next alone is 14.4 KiB br (measured).
- **Bidi hygiene is mandatory.** Wrap phone numbers, Latin product names and SKUs in `<bdi>` or `dir="ltr"` isolates. Without that, a phone number written with spaces renders in scrambled group order in Arabic (I demonstrated this, see table row 17). Normalise Eastern Arabic digits (U+0660–0669 and U+06F0–06F9) to ASCII on the server.
- **Design for 360 CSS px first.** 360×800 is the top Algerian mobile resolution at 19%. Implement WCAG 2.2 AA with CSS only: tap targets ≥44px (the AA floor is 24px), `scroll-padding` under the sticky header and bottom bar, contrast tokens checked at 4.5:1, `lang` on mixed-language spans, and `prefers-reduced-motion`.

## 3. Alternatives considered and rejected

- **Separate RTL stylesheet via rtlcss.** Row 20: per-visitor bytes are the same, but it doubles build output and cache entries, and a visitor who switches language downloads twice. Logical properties do the same job with one file, and rtlcss found nothing to flip.
- **Google Fonts CSS API, or Cloudflare Fonts on top of it.** Rows 12 and 24: 162.3 KiB vs 21.0 KiB for Noto Sans Arabic, because Google ships every axis. Google also adds a cross-origin connection, which matters on high-latency Algerian networks; that latency figure belongs to the network teammate. For static fonts like Tajawal, Google's file is about the same size as mine, so the gain comes from pinning the variable axes.
- **System Arabic font only (0 bytes).** Defensible, and it is the fallback if the spike shows any LCP or CLS regression. I rejected it as the default for three reasons:
  - Android's system Arabic is Noto Naskh (row 10), a book-style naskh, so it is not a UI sans.
  - OEM skins may replace it with fonts we cannot test.
  - The web font only costs about 21 KiB and, with `optional`, cannot delay rendering or shift layout. That makes this a bandwidth cost only, not a speed-metric conflict.
- **Readex Pro / Alexandria / Cairo / Tajawal / Almarai as the default.** They are 1–12 KiB smaller (row 13) but lack ڨ/ڢ/ڧ (row 14). Any missing glyph falls back to another font mid-word, which breaks the cursive joining. They stay acceptable if the client's content team confirms they never use these letters. Tajawal at 9.4 KiB is the smallest.
- **IBM Plex Sans Arabic.** Its width is closest to Naskh (105%, the lowest reflow risk), but it costs 19.4 KiB per static weight, so about 39 KiB for two weights, and it lacks ڢ.
- **`font-display: swap` with metric-override fallbacks.** Rows 9 and 15: `ascent-override` is missing on iOS. The fallback differs by OS (Naskh on Android, SF Arabic on iOS). Paragraph width differs by 5–27% and `line-height: normal` varies from 1.20 to 2.11em. A single override set cannot match both platforms, so swap carries CLS risk. `optional` removes it.
- **GSAP, Framer Motion/`motion`, React-based UI.** Row 21: 25–100 KiB br, plus main-thread time on G85/T606-class CPUs. CSS replacements cover 95–98% of Algerian mobile traffic (row 8), and unsupported browsers simply skip the animation. `motion/mini` (3.3 KiB) is the only acceptable fallback if one specific effect proves impossible in CSS.
- **Client-side i18n (i18next, react-i18next).** Row 22: 14.4 KiB br with no benefit, because pages are rendered per language.
- **Accept-Language auto-redirect at the edge.** Row 23: Google advises against it and Googlebot sends no Accept-Language. At most, use `/` as an `x-default` language chooser or a soft banner.

## 4. Interface assumptions (for others to challenge)

- **Rendering/framework:** fully server- or statically-rendered HTML per language, with no hydration on catalogue pages. Inline CSS budget ≤ about 5 KiB br. If the framework forces a JS runtime, my zero-JS motion and i18n position needs re-checking.
- **If SSR is in Rust:** `Intl` is unavailable, so format DZD and dates with a small Rust formatter (integer DZD with `.` grouping and Western digits) or with ICU4X. Either way, match the `ar-DZ`/`fr-DZ` output in rows 18–19. Tailwind v4 has a standalone CLI binary, so no Node is needed at runtime.
- **Hosting/CDN:** fonts are served from the same origin as the HTML over the same HTTP/2 or HTTP/3 connection, with `Cache-Control: immutable` and content-hashed names. Preload goes only on `/ar/` pages.
- **Performance teammate:** decides whether the LCP element is text or the product image. With `optional`, the font should never be on the LCP path. **Please verify in the spike how Lighthouse treats a preloaded `optional` font.**
- **Orders/anti-spam teammate:**
  - The phone input uses `type="tel"`, `inputmode="tel"`, `autocomplete="tel"` and `dir="ltr"`, and the server normalises Eastern Arabic digits.
  - The wilaya and commune lists must be the **69-wilaya / 1,541-commune** set with Arabic and French names.
  - The no-JS commune picker (a native `<select>` with an optgroup per wilaya, or a server round-trip) still needs its bytes measured.
  - Any CAPTCHA (e.g. Turnstile) must not add an interactive cognitive test.
- **CMS/admin teammate:**
  - Every content field is bilingual (`*_fr`, `*_ar`) with per-language slugs, plus a "Latin brand name" field so the renderer can wrap it in `<bdi lang="…">`.
  - The admin can be French-only with system fonts; it has a separate JS budget.
- **Gotcha for everyone:** the language switcher label «العربية» on French pages would trigger the Arabic font download through `unicode-range`. Give the switcher a system-font family.

## 5. Risks, open questions, and where evidence is thin

- **Thin: OEM Arabic fonts.** I have no data on what Samsung One UI, Xiaomi HyperOS, Oppo ColorOS or Infinix XOS actually render for Arabic in Chrome. That matters for the system-font fallback and for what `optional` falls back to. It needs a real-device screenshot pass (Galaxy A-series, Redmi, Infinix).
- **Thin: Algerian device models and CPU.** StatCounter gives vendors and resolutions only. The CPU figures are chipset proxies (row 29). That 360×800 means budget 720×1600 phones at DPR 2 is my inference.
- **Thin: Arabic shaping cost on real phones.** My numbers come from a desktop CPU in Python. A rough scaling (desktop to G85 at about 2.5–3×) suggests about 10–30 ms of shaping for a 3–4k-character product page on a low-end phone. That is a rough estimate, so measure it in a Chrome trace on a G85-class device.
- **Thin: digit entry on keyboards.** Whether Gboard or iOS Arabic keyboards emit Eastern digits by default in Algeria is unverified, so normalise regardless.
- **Thin: TalkBack language switching.** Whether TalkBack honours `lang` on inline spans (French names inside Arabic) is unverified. Arabic TTS support itself is documented (row 25). Manual testing is needed.
- **Thin: ڨ/ڢ in commercial copy.** How often they appear in Algerian e-commerce text is unknown; coverage is measured, frequency is not. Ask the client.
- **Open: `optional` on first visit.** On a slow first load the brand font may not show at all on that page, which is a design trade-off. The spike should measure how often the font arrives within the block period on Algerian networks.
- **Open: cross-document View Transitions and real-user LCP.** Lighthouse is unaffected because it loads pages cold. I found no evidence either way for real-user LCP on later navigations, so field data (RUM/CrUX) is needed after launch.
- **Caveats on the feature-support figures.**
  - caniuse counts all Chrome Android traffic as the latest version.
  - Android 7 devices (frozen at Chrome 119) lack `@view-transition`, and Android 8/9 (Chrome 138) support everything recommended here.
  - All of these features are progressive enhancement, so the downside is "no animation", not breakage.
- **Stale sources:** the SF Arabic forum posts (2017–2020) and the letter-spacing tests (2019–2022). Rule: never apply `letter-spacing` to Arabic; reset it under `:lang(ar)`.
- **Accessibility risks that conflict with a "premium" look.** Low-contrast grey-on-cream text fails 1.4.3. Auto-advancing hero carousels need a pause control under 2.2.2. Fixed-height text boxes break under 1.4.12 text spacing and with Arabic's 1.6–1.8 line-height.
- **Maintenance.**
  - Re-run the subsetting pipeline whenever the font or the content's character set changes. It takes about 1 minute.
  - Track the Algerian figures on caniuse and StatCounter each quarter.
  - The 69-wilaya list may still change: the 2025 reform had press coverage of further administrative changes.
